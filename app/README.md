# Unscramble Game

## Описание проекта

**Unscramble Game** — это интерактивная игра для Android, в которой игроку предлагается угадывать перемешанные слова. Игра состоит из 10 вопросов, за каждый правильный ответ начисляется 20 очков. После ответа на все вопросы показывается итоговый счёт с возможностью начать игру заново.

## Технологии

Проект разработан с использованием современных технологий Android-разработки:

- **Kotlin** — основной язык программирования
- **Jetpack Compose** — современный инструментарий для создания UI
- **ViewModel** — компонент архитектуры для управления данными UI
- **StateFlow** — реактивный поток данных для обновления интерфейса
- **Material Design 3** — дизайн-система от Google
- **Android Architecture Components** — компоненты архитектуры Android Jetpack
- **JUnit** — фреймворк для модульного тестирования

## Функциональность приложения

### Основные возможности:

1. **Игровой процесс**
   - Отображение перемешанных слов из предустановленного списка
   - Ввод ответа пользователем через текстовое поле
   - Проверка правильности ответа (без учёта регистра)
   - Подсчёт очков (+20 за каждый правильный ответ)
   - Отслеживание прогресса (вопрос X из 10)

2. **Управление игрой**
   - Кнопка "Проверить" — проверка введённого ответа
   - Кнопка "Пропустить" — переход к следующему слову без начисления очков
   - Визуальная индикация неправильного ответа (красный цвет)
   - Автоматический переход к следующему слову после правильного ответа

3. **Завершение игры**
   - Диалоговое окно с итоговым счётом после 10 вопросов
   - Кнопка "Играть снова" для перезапуска игры
   - Сброс всех использованных слов при новой игре

4. **Сохранение состояния**
   - Сохранение данных при повороте экрана
   - Сохранение состояния при смене темы
   - Корректная работа при изменении конфигурации устройства

5. **Тестирование**
   - Модульные тесты для проверки логики игры
   - Тесты пути успеха (правильные ответы)
   - Тесты пути ошибки (неправильные ответы)
   - Тесты граничных случаев (инициализация, завершение игры)

## Контрольные вопросы

### 1. Что такое ViewModel и зачем он нужен?

**ViewModel** — это компонент архитектуры Android Jetpack, предназначенный для хранения и управления данными пользовательского интерфейса.

**Какую проблему решает:**
- Без ViewModel данные в Composable-функциях хранятся в локальных переменных (`remember`), которые уничтожаются при изменении конфигурации (поворот экрана, смена темы)
- При повороте экрана Android полностью уничтожает Activity и создаёт её заново, что приводит к потере всех данных игры (счёт, текущее слово, прогресс)
- ViewModel сохраняет данные при configuration changes, так как живёт дольше, чем UI-компоненты

**Пример проблемы без ViewModel:**
```kotlin
// Обычные переменные в Composable
var score by remember { mutableStateOf(0) }
// После поворота экрана score снова будет 0!
```

### 2. В чём разница между MutableStateFlow и StateFlow?

**MutableStateFlow** — изменяемый поток данных:
- Позволяет изменять значение через `.value`
- Может быть изменён только внутри ViewModel
- Используется для внутренней логики

**StateFlow** — неизменяемый (только для чтения) поток:
- Можно только читать значение
- Нельзя изменить извне
- Предоставляется UI для наблюдения

**Зачем два поля (_uiState и uiState):**
```kotlin
private val _uiState = MutableStateFlow(GameUiState())  // Изменяемое (для ViewModel)
val uiState: StateFlow<GameUiState> = _uiState.asStateFlow()  // Только для чтения (для UI)
```

**"Backing property pattern"** (паттерн опорного свойства):
- `_uiState` — приватное изменяемое свойство (префикс `_` обозначает внутреннюю переменную)
- `uiState` — публичное свойство только для чтения
- UI может наблюдать за изменениями, но не может изменять состояние напрямую
- Это защищает от случайных изменений и делает код более предсказуемым

### 3. Почему в ViewModel нельзя хранить Context или View?

**Причины:**

1. **Утечки памяти (Memory Leaks):**
    - ViewModel живёт дольше, чем Activity/Fragment
    - Если сохранить ссылку на Context (Activity), то Activity не сможет быть уничтожен сборщиком мусора
    - Это приведёт к утечке памяти и возможному краху приложения

2. **Нарушение архитектуры:**
    - ViewModel должен быть независим от UI
    - Это позволяет легко тестировать ViewModel без Android-фреймворка
    - Разделение логики и представления — принцип чистой архитектуры

3. **Проблемы с жизненным циклом:**
    - Context может быть уничтожен, а ViewModel продолжает жить
    - Ссылка на уничтоженный Context приведёт к исключениям

**Правильный подход:**
- Передавать данные из ViewModel в UI через StateFlow
- UI сам работает с Context и View

### 4. Чем StateFlow отличается от remember и rememberSaveable?

**remember:**
```kotlin
var score by remember { mutableStateOf(0) }
```
- Хранит данные только в Composable-функции
- **Не переживает** поворот экрана ❌
- **Не переживает** смерть процесса ❌
- Простое использование, но ненадёжно

**rememberSaveable:**
```kotlin
var score by rememberSaveable { mutableStateOf(0) }
```
- Сохраняет данные в Bundle
- **Переживает** поворот экрана ✅
- **Переживает** смерть процесса ✅
- Ограничен простыми типами данных (Int, String, Boolean)

**StateFlow:**
```kotlin
private val _score = MutableStateFlow(0)
val score: StateFlow<Int> = _score
```
- Хранит данные в отдельном классе (ViewModel)
- **Переживает** поворот экрана ✅
- **Не переживает** смерть процесса ❌
- Идеально для UI-логики
- Автоматически уведомляет UI об изменениях
- Thread-safe (безопасен для многопоточности)
- Работает по принципу "подписки"

**Когда что использовать:**
- `remember` — для временных данных внутри одной Composable (открыто/закрыто меню)
- `rememberSaveable` — для простых данных, которые нужно сохранить (текст в поле ввода)
- `StateFlow + ViewModel` — для сложной бизнес-логики и состояния всего экрана

### 5. Что такое data class в Kotlin и зачем он используется для UI State?

**data class** — специальный тип класса в Kotlin, предназначенный для хранения данных.

**Автоматически генерируемые методы:**
1. `equals()` — сравнение двух объектов на равенство
2. `hashCode()` — вычисление хэш-кода
3. `toString()` — строковое представление объекта (для отладки)
4. `copy()` — создание копии объекта с изменением отдельных полей

**Пример:**
```kotlin
data class GameUiState(
    val currentScrambledWord: String = "",
    val currentWordCount: Int = 1,
    val score: Int = 0,
    val isGuessedWordWrong: Boolean = false,
    val isGameOver: Boolean = false
)
```

**Зачем используется для UI State:**

1. **Всё состояние в одном месте:**
    - Вместо множества отдельных переменных — один объект
    - Легко понять, что отображается на экране

2. **Неизменяемость (immutability):**
    - Все свойства `val` (неизменяемые)
    - Предсказуемое состояние

3. **Функция copy():**
```kotlin
// Обновляем только score, остальные поля остаются прежними
currentState.copy(score = updatedScore)
```
- Создаёт новый объект с изменёнными полями
- Не нужно вручную копировать все поля
- Удобно для обновления StateFlow

4. **Легко тестировать:**
    - Можно создать объект с конкретными значениями
    - Простая проверка равенства через `equals()`

### 6. Как работает collectAsState() в Compose?

**collectAsState()** — функция расширения, которая преобразует StateFlow в State, наблюдаемый Compose.

**Механизм работы:**

1. **Подписка на изменения:**
```kotlin
val gameUiState by gameViewModel.uiState.collectAsState()
```
- UI "подписывается" на изменения StateFlow
- При изменении `_uiState.value` в ViewModel, UI автоматически получает уведомление

2. **Автоматическая перерисовка:**
```kotlin
// В ViewModel
_uiState.value = GameUiState(score = 20)

// В Composable
Text("Счёт: ${gameUiState.score}")  // Автоматически обновится!
```
- Когда StateFlow изменяется, Compose помечает Composable-функцию как "грязную"
- При следующей перерисовке функция вызывается заново с новыми данными

3. **Почему UI обновляется автоматически:**
    - StateFlow реализует паттерн Observer (Наблюдатель)
    - collectAsState() создаёт State, который отслеживает изменения
    - Compose реагирует на изменения State и перерисовывает UI
    - Это называется "реактивное программирование"

**Аналогия:**
- StateFlow — это радио, которое транслирует музыку
- collectAsState() — это ваш приёмник, настроенный на волну
- Когда на радио меняется песня (данные), вы автоматически слышите новую (UI обновляется)

### 7. Зачем разделять код на пакеты data и ui?

**Принципы архитектуры:**

1. **Разделение ответственности (Separation of Concerns):**
    - `data` — хранение данных и моделей
    - `ui` (или `ui_model`) — логика отображения и управления UI

2. **Что в пакете data:**
    - `GameUiState.kt` — модели данных (data classes)
    - `WordsData.kt` — константы и списки слов
    - Только данные, без логики

3. **Что в пакете ui_model:**
    - `GameViewModel.kt` — бизнес-логика игры
    - `GameScreen.kt` — Composable-функции (UI)
    - Логика управления состоянием

**Преимущества:**

1. **Чистота кода:**
    - Легко найти нужный файл
    - Понятная структура проекта

2. **Поддержка:**
    - Изменение данных не влияет на UI
    - Изменение UI не ломает модели данных

3. **Масштабируемость:**
    - Можно добавлять новые функции без хаоса
    - Несколько разработчиков могут работать параллельно

4. **Тестируемость:**
    - Модели данных можно тестировать отдельно
    - ViewModel тестируется без UI

5. **Принципы, которые это поддерживает:**
    - **SOLID** (Single Responsibility Principle)
    - **Clean Architecture** (разделение слоёв)
    - **MVVM** (Model-View-ViewModel)

### 8. Что происходит с ViewModel, когда приложение полностью закрывается (process death)?

**Process Death (смерть процесса):**
- Когда Android убивает приложение из-за нехватки памяти
- Или когда пользователь закрывает приложение из списка недавних
- Или при явном вызове `System.exit()`

**Что происходит с ViewModel:**

1. **ViewModel НЕ сохраняется:**
    - ViewModel хранит данные в оперативной памяти (RAM)
    - При уничтожении процесса вся память освобождается
    - Все данные в ViewModel теряются 

2. **Сравнение подходов:**

| Подход | Переживает поворот? | Переживает process death? |
|--------|-----------------|-----------------------|
| remember | Нет | Нет |
| rememberSaveable | Да  | Да  |
| ViewModel | Да  | Нет |
| Database/SharedPreferences | Да  | Да  |

**Альтернативы для долговременного хранения:**

1. **SharedPreferences:**
    - Для простых данных (настройки, флаги)
    - Хранится на диске в XML-файле

2. **Room Database:**
    - Для сложных структурированных данных
    - Полноценная SQLite база данных

3. **DataStore:**
    - Современная замена SharedPreferences
    - Поддерживает Flow (реактивность)

4. **Saved State Handle (в ViewModel):**
    - Специальный механизм для сохранения состояния ViewModel
    - Использует Bundle для сохранения
    - Переживает process death

**Пример с Saved State:**
```kotlin
class GameViewModel(
    private val savedStateHandle: SavedStateHandle
) : ViewModel() {
    private val _score = MutableStateFlow(savedStateHandle.get<Int>("score") ?: 0)
    
    fun updateScore(newScore: Int) {
        _score.value = newScore
        savedStateHandle["score"] = newScore  // Сохраняем
    }
}
```
